## TL;DR — Decisions

| # | Decision | Basis |
|---|----------|-------|
| **D-A** | **A "context" = one `(subjectProfile × trainer)` pair**, drawn from that profile's *active* associations. Two axes, never one. | BR-004 (M:N per profile) + BR-005 (no unified view) |
| **D-B** | **Three data zones:** Family/Account (global) · Per-subject (the person, regardless of coach) · Per-context (the `(subject,trainer)` channel). The switcher governs only the per-context zone. | BR-007 splits family vs per-trainer data |
| **D-C** | **Switcher shape = subject switch + trainer tabs.** Pick the person (account-style), then their coaches appear as tabs. Progressive disclosure collapses any single-option axis → a 1-subject/1-trainer user sees **no switcher at all**. | FR-027 mental model; scales with family size |
| **D-D** | **Active context travels per-request and is authorized server-side** (header → guard → CLS), **not** baked into the JWT. Browser remembers last context; server stores a default for fresh logins. | No token churn; multi-tab; refresh-rotation untouched |
| **D-E** | **Cross-context alerts live in the global account zone**, each labeled with its channel; clicking one switches into that channel. | Lets a parent learn of work in another channel without a merged data view (BR-005) |
| **D-F** | **"Best Times" = one shared schedule per child**, visible to all that child's trainers (per-subject, not per-context). ⚠️ *flagged* — see §10. | Simplicity; matches current Availability entity (no `trainerId`) |

## 1. What a "context" is

A parent account can hold several **players** — the parent themselves (if they also train, FR-020) **plus** each child. Each player associates with **multiple trainers** (BR-004, M:N), and the rules forbid ever showing those relationships merged (BR-005). So the app is always "tuned" to exactly one **`(subjectProfile, trainer)`** pair — *who* + *which coach*. That pair is the **context**. Switching context is account-switch-like (the scoped view reloads), **not** filtering.

**Worked example — parent "Dana", who also trains herself:**

| Subject | Active trainers | Contexts |
|---------|-----------------|----------|
| Dana (self) | Jones | `Dana→Jones` |
| Emma (child) | Smith, Lee | `Emma→Smith`, `Emma→Lee` |
| Liam (child) | Smith | `Liam→Smith` |

→ **4 contexts.** There is never a 5th "all of Emma" or "Dana's family" merged screen.

---

## 2. Three data zones

BR-007 ("parent owns family contact info; each child has independent calendar/RSVP/Best-Times per trainer") splits the data into layers. The Best-Times decision (§9) pulls per-subject data into its own middle layer:

| Zone | Scoped by switcher? | Contains | Basis |
|------|---------------------|----------|-------|
| **1 · Family / Account** | ❌ always global | parent contact info, children roster, manage child↔trainer associations, pending approvals, **notifications** (§8), security/account settings | BR-007 (parent owns family data) |
| **2 · Per-subject** | partial (subject only) | the person's profile basics, skill level, **Best Times availability** (§9) | "things true about Emma regardless of coach" |
| **3 · Per-context** `(subject × trainer)` | ✅ full | dashboard, calendar/events, RSVPs, trainer content (Epic-04), tokens/purchases (Epic-05), messages with that trainer | BR-005 + BR-007 (independent per trainer) |

Zone 1 stays visible to the parent regardless of active context. A **logged-in child** sees **no Zone 1** and a fixed subject (themselves) — only their Zone 3 trainer-tabs (depends on the minor-login model, §10).

## 3. Switcher UX (D-C)

```
 [ Dana ▾ ]              ← Zone-1 account-style "who" switcher
   ├ Me (Dana)
   ├ Emma
   └ Liam

 Emma ▸ [ Coach Smith | Coach Lee ]    ← trainer tabs for the chosen subject
         └─ Zone-3 workspace: dashboard / calendar / RSVPs / content /
            tokens / messages — for Emma, as Coach Smith sees it, ONLY
```

- **Two cognitive acts kept separate:** *who am I managing* (subject) vs. *which relationship* (trainer).
- **Progressive disclosure:**
  - 1 subject + 1 trainer → no switcher, no tabs (the common case is friction-free).
  - 1 subject + N trainers → tabs only.
  - N subjects → subject switcher + tabs.
- **Child user:** subject is fixed to self (no subject switcher); only trainer tabs render.

## 4. Data-scoping & enforcement (D-D)

The browser tells the server the active context on **every** request; the server **authorizes it every time** and loads it into request context. Nothing about the active context is trusted from the client without a check.

```
client ──X-Active-Context: <subjectProfileId>:<trainerId>──▶ TenantGuard
   guard verifies, every request:
     (a) subjectProfileId belongs to the current user
         (own profile, or a child they are the parent of)
     (b) the (subjectProfileId, trainerId) association exists AND is active
   on pass  → write { activeSubjectProfileId, activeTrainerId } into nestjs-cls
   on fail  → 403 CONTEXT_FORBIDDEN (or 410 if the association went inactive → client bounces, §5)
```

**Wiring into the existing tenancy layer** (`specs/architect-architecture.md` §Multi-Tenancy):
- `activeTrainerId` → drives the existing `ScopedRepository` (`where(eq(table.trainerId, ctx.trainerId))`) **and** the per-transaction RLS GUC `SET LOCAL app.current_trainer_id`.
- `activeSubjectProfileId` → an **additional** filter for subject-scoped reads/writes (e.g. *this child's* RSVPs within that trainer).
- Context resolution is **TenantGuard's job**, extended to resolve + validate the subject as well as the trainer.

**Why per-request, not JWT claim:** switching context must not mint a new auth token; a parent can keep *Emma* in one browser tab and *Liam* in another (a single shared cookie/claim can't); refresh-rotation stays untouched.

**Persistence ("context persists across session", FR-019):**
- Browser remembers the last active context (localStorage) and re-sends it.
- Server stores a per-user **default context** preference, used to seed fresh logins (§5).

## 5. Behaviors

| Situation | Behavior |
|-----------|----------|
| **Login landing** | Resume last context. First-timer / single context → drop straight in. Multiple contexts + no history → a "Who are you managing today?" picker (Zone 1). |
| **Association removed mid-session** (FR-023) | Server returns the bounce signal; client switches to a safe default context and shows a *"that connection was removed"* toast — never a broken/empty scoped screen. |
| **Trainer / Coach / Super Admin** | **No switcher.** Their world is fixed to their own organization (coach → one trainer; trainer → own org). |
| **Logged-in child** | Own trainer-tabs only; no subject switcher; no Zone 1. *(Leans on the minor-login model, §10.)* |
| **Just joined a coach via ShareLink** (FR-017/018) | New context appears in the switcher immediately and the user is dropped into it. |
| **Super Admin impersonating a parent** (FR-015) | Sees the exact same switcher the parent sees. |
| **Empty state** | Child added but no coach joined yet → subject shows with a "connect a coach" prompt instead of tabs. |
| **Deep links** (email/bookmark) | URL carries the channel (e.g. `/c/:subjectProfileId/:trainerId/...`); opening it re-validates entitlement before rendering. |

## 6. Server contract sketch (for `api-designer`)

> Shapes only — final contract owned by the api-designer pass.

| Endpoint / header | Purpose |
|-------------------|---------|
| `GET /me/contexts` | Feeds the switcher: `{ subjects: [{ profileId, displayName, isSelf, isChild, trainers: [{ trainerId, name, status }] }], defaultContext }` |
| `X-Active-Context: <subjectProfileId>:<trainerId>` | Sent on every Zone-3 (and subject-scoped Zone-2) request; validated by TenantGuard. |
| `PUT /me/contexts/default` | Persist the user's default context preference. |
| Error `403 CONTEXT_FORBIDDEN` | User not entitled to the requested context. |
| Error `410 CONTEXT_INACTIVE` | Association went inactive → client bounces to a safe default (§5). |

## 8. Cross-context notifications (D-E)

The "no merged views" rule (BR-005) creates one friction point: a parent in *Emma+Smith* still needs to learn that *Liam+Jones* has a purchase awaiting approval. Resolved by a **notifications bell in the global account zone (Zone 1)**:

- Each alert is **labeled with its channel** — e.g. *"Liam · Coach Jones — approval needed"*.
- Clicking an alert **switches the active context** into that channel and deep-links to the item.
- This is compliant because it is an **alert list**, not a merged data screen — Liam's calendar is never rendered beside Emma's.

---

## 9. Best Times scoping (D-F) — ⚠️ flagged

**Decision:** "Best Times" is **one shared schedule per child** (Zone 2), visible to all of that child's trainers. Set once via the subject (not per trainer-tab).

**Rationale:** a child's general availability rarely differs by coach; one schedule is far simpler; it matches the architecture's `Availability` entity, which keys on `subjectId` with **no `trainerId`**.

**The flag:** a strict reading of **BR-007** ("each child has independent … Best-Times **per trainer**") could mean **per-coach** schedules. The written rule and the current data model disagree.
- If the client confirms shared-per-child → **no change** (current model holds; Best Times stays Zone 2).
- If the client wants per-coach → `Availability` gains a `trainerId`, Best Times moves into **Zone 3**, and FR-034/FR-039 UIs render per-tab. **Confirm with client before building `availability/`.**
